# بخش اول — واژگان آزمون و پذیرش

## 6. آزمون واحد

آزمونی است که یک واحد کوچک رفتاری را با وابستگی‌های محدود بررسی می‌کند.

آزمون واحد باید:

- سریع باشد؛
- قابل تکرار باشد؛
- دلیل شکست روشن داشته باشد؛
- رفتار، نه جزئیات تصادفی پیاده‌سازی، را بررسی کند.

## 7. آزمون مؤلفه

آزمونی است که یک مؤلفه UI، Adapter یا واحد نسبتاً مستقل را با مرزهای نزدیک خود بررسی می‌کند.

آزمون مؤلفه با آزمون مرورگر کامل یکسان نیست.

## 8. آزمون قرارداد

آزمونی است که سازگاری Producer، Consumer، Server، Client یا Message Handler را با Contract مصوب بررسی می‌کند.

موارد هدف:

- Schema؛
- نوع؛
- فیلد اجباری؛
- کد خطا؛
- نسخه؛
- سازگاری عقب‌رو؛
- Payload پیام.

## 9. آزمون یکپارچه

آزمونی است که حداقل یک مرز واقعی میان دو جزء را بررسی می‌کند.

نمونه:

- API و PostgreSQL؛
- Worker و Redis؛
- Scheduler و PostgreSQL؛
- فایل و MinIO؛
- Web و API؛
- Outbox و Consumer.

## 10. آزمون سرتاسری

آزمونی است که یک گردش اصلی محصول را از ورودی کاربر تا نتیجه قابل مشاهده و پایدار بررسی می‌کند.

نمونه آینده:

- ایجاد پرونده؛
- ارجاع؛
- پذیرش مسئولیت؛
- ثبت نتیجه؛
- تعیین ادامه معتبر؛

## 11. آزمون دود

آزمون سریع و محدود برای اثبات اجرای پایه سامانه یا محیط است.

آزمون دود جایگزین آزمون کامل رفتار نیست.

## 12. آزمون پذیرش

آزمونی است که خروجی مرحله را در برابر معیارهای مصوب همان مرحله ارزیابی می‌کند.

پذیرش ممکن است ترکیبی از موارد زیر باشد:

- آزمون خودکار؛
- اجرای واقعی؛
- ممیزی دستی کنترل‌شده؛
- بررسی امنیت؛
- بررسی مستندات؛
- Commit و Tag.

## 13. آزمون بازگشتی

آزمونی است که از بازگشت یک خطا یا رفتار نامعتبر قبلی جلوگیری می‌کند.

هر خطای واقعی اصلاح‌شده باید در صورت امکان آزمون بازگشتی داشته باشد.

## 14. آزمون منفی

آزمونی است که ردشدن ورودی، دسترسی، وضعیت یا رابطه نامعتبر را بررسی می‌کند.

آزمون منفی برای دامنه، امنیت و چندسازمانی الزامی است.

## 15. آزمون هم‌زمانی

## 16. آزمون هم‌کنشی امن

آزمونی است که اجرای دوباره عملیات منطقی واحد را بررسی می‌کند و باید ثابت کند اثر تجاری تکراری ایجاد نمی‌شود.

## 17. آزمون معماری

آزمونی است که مرزهای وابستگی و قواعد ساختاری را بررسی می‌کند.

نمونه:

## 18. آزمون امنیت

## 19. آزمون کارایی

## 20. آزمون بازیابی

## 152. کنترل آمادگی بدون توقف تصمیم

پیش از نخستین تغییر رابط باید این کنترل‌ها موفق باشند:

- سه مخزن مرجع در مسیر بیرونی مصوب موجود باشند
- Commit هر مرجع با مقدار منجمدشده برابر باشد
- هر مرجع Detached و پاک باشد
- مجوز `MIT` هر سه مرجع موجود و قابل‌ردیابی باشد
- هیچ کد یا وابستگی از مرجع‌ها بدون ممیزی فایل‌به‌فایل وارد نشده باشد
- فونت `Vazirmatn` فقط به‌صورت محلی و همراه مجوز معتبر اضافه شود
- معماری Contract هویت مجوز چندسازمانی و Backend OrgaWork مرجع نهایی باقی بمانند

شکست این کنترل‌ها توقف فنی برای رفع مشکل است و به معنی بازگشایی تصمیم طراحی نیست.

## 153. معیارهای رابط

- متن عمومی کاملاً فارسی

- زمان فنی `UTC`
- کنترل متن ترکیبی و بخش‌های فنی `LTR`
- دسترس‌پذیری صفحه‌کلید و Focus
- آزمون در اندازه‌های مختلف صفحه
- نبود انتقال منطق `Clerk` `Sentry` Billing Auth Authorization Tenancy یا Backend قالب‌ها
- یکنواختی زبان بصری بر پایه `Studio Admin` و جلوگیری از ترکیب ظاهری ناسازگار سه قالب

# پیوست جاری — سیاست Orchestration آزمون و پذیرش

اصل چندلایه و سخت‌گیرانه آزمون تغییر نکرده است؛ تغییر فقط در Orchestration است تا Suite متناسب با ریسک اجرا شود و تست‌های نامرتبط باعث اتلاف زمان نشوند.

## پروفایل‌های رسمی

- `fast`: برای بازخورد توسعه و فقط دامنه تغییر.
- `stage`: برای پذیرش زیرمرحله و بر اساس Gate Registry همان Stage.
- `full`: برای پذیرش کلان، تغییر Foundation/CI و ممیزی جامع.
- `infra`: برای تغییرهای Migration، RLS، معماری و امنیت زیرساخت.
- `ci`: پروفایل داخلی برای Suiteهای موازی GitHub Actions؛ تعریف Gateها همچنان در یک Registry مرکزی است.

GitHub Actions نباید منطق Gate را دوباره در YAML تعریف کند؛ Workflow فقط Suite نام‌دار Runner را فراخوانی می‌کند.

## شاهد معتبر اختتام

اختتام زیرمرحله فقط وقتی مجاز است که:

- آخرین گزارش `verify:stage` برابر PASS باشد؛
- گزارش متعلق به همان Stage و همان Technical Commit باشد؛
- Verification روی Worktree پاک اجرا شده باشد؛
- Stage-specific closure evidence gate در Registry تعریف و PASS شده باشد؛
- مستندات Closure تولید و بازبینی شده باشند؛
- Closure Commit و Tag پذیرش ایجاد شوند؛
- Push شاخه و Tag به‌صورت Atomic موفق باشد؛
- Remote و Worktree پاک پس از Push تأیید شوند.

این Orchestration کاهش معیار آزمون نیست؛ Suiteهای واقعی، آزمون منفی، Integration، Migration/RLS و Smoke همچنان باید در Gate مناسب Stage ثبت شوند.

## تفکیک پذیرش تاریخی از وضعیت جاری

- Historical Acceptance فقط شواهد زمان بسته‌شدن Stage را بررسی می‌کند و وضعیت جاری را منجمد نمی‌کند.
- Current-State Invariants وضعیت امروز Roadmap و Project Status را با شناسه Stage، نه عنوان متنی، بررسی می‌کنند.
- P1.10 ترتیب Type Declaration پیش از Lint را از Registry مرکزی `ciSuiteGateIds` بررسی می‌کند، نه از متن YAML.
- Timeout مرکزی: Unit=5s، Acceptance/CI=30s و Publication=60s.
- `vitest.acceptance.config.ts` و `vitest.ci.config.ts` از policy مرکزی استفاده می‌کنند.
