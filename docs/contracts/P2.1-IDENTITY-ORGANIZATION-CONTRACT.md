# قرارداد دامنه هویت و سازمان P2.1

## 1. شناسنامه

- شناسه: `P2.1-IDENTITY-ORGANIZATION-CONTRACT`
- نسخه: `1.0.0`
- وضعیت: پذیرفته‌شده برای اجرای مراحل `P2.2` تا `P2.12`
- مالک: `P2 — هویت، سازمان و مجوزدهی`
- مرز: قرارداد دامنه و امنیت
- خارج از دامنه: پیاده‌سازی مدل، Migration، Endpoint اجرایی و رابط کاربری

## 2. هدف

این سند واژگان، وضعیت‌ها، ناوردایی‌ها و تصمیم‌های امنیتی لازم برای مراحل هویت، سازمان، نشست، مجوز، دعوت و تیم را تثبیت می‌کند.

وجود این سند به معنی پیاده‌سازی قابلیت‌ها نیست. هر قابلیت فقط در مرحله مالک خود ایجاد و آزموده می‌شود.

## 3. اصول حاکم

1. هویت سراسری کاربر از عضویت سازمانی جدا است.
2. یک کاربر می‌تواند عضو چند سازمان باشد.
3. هر درخواست سازمانی دقیقاً یک سازمان جاری معتبر دارد.
4. احراز هویت به‌تنهایی مجوز منبع ایجاد نمی‌کند.
5. پیش‌فرض دسترسی عدم دسترسی است.
6. عدم دسترسی صریح بر اجازه اولویت دارد.
7. داده سازمان قبلی پس از تغییر سازمان جاری نباید باقی بماند.
8. PostgreSQL منبع حقیقت وضعیت پایدار هویت و نشست است.
9. Secret و PII در Log یا Audit خام ثبت نمی‌شوند.
10. طراحی واقعی رابط کاربری پیش از `P2.13` ممنوع است.

## 4. موجودیت‌های مفهومی

### 4.1 کاربر

`User` هویت انسانی سراسری در سامانه است و به سازمان خاصی وابسته نیست.

وضعیت‌های قطعی:

- `pending`
- `active`
- `disabled`

کاربر غیرفعال اجازه ورود یا استفاده از نشست موجود را ندارد و تمام نشست‌های فعال او باید لغو شوند.

### 4.2 اعتبارنامه گذرواژه

`PasswordCredential` اعتبارنامه ورود مبتنی بر گذرواژه برای یک کاربر است.

در نسخه نخست هر کاربر حداکثر یک اعتبارنامه گذرواژه فعال دارد. ساختار دامنه باید امکان افزودن روش‌های ورود دیگر را بدون ادغام هویت با عضویت حفظ کند.

### 4.3 سازمان

`Organization` مرز اصلی مالکیت، امنیت و جداسازی داده است.

هر منبع سازمانی دقیقاً یک سازمان مالک دارد.

### 4.4 عضویت

`Membership` رابطه کاربر و سازمان است.

وضعیت‌های قطعی:

- `invited`
- `active`
- `suspended`
- `revoked`

فقط عضویت `active` امکان انتخاب سازمان و ارزیابی مجوز را ایجاد می‌کند.

تغییر وضعیت یک عضویت نباید عضویت‌های دیگر همان کاربر را تغییر دهد.

### 4.5 تیم

`Team` فقط درون یک سازمان وجود دارد.

`TeamMembership` فقط میان تیم و عضویت فعال همان سازمان معتبر است.

نقش تیمی مدیر یا ناظر تیم با نقش سازمانی و مجوز منبع یکسان نیست.

### 4.6 دعوت

`Invitation` درخواست کنترل‌شده برای ایجاد یا فعال‌کردن عضویت در یک سازمان است.

وضعیت‌های قطعی:

- `pending`
- `accepted`
- `revoked`
- `expired`

دعوت مصرف‌شده، لغوشده یا منقضی قابل استفاده دوباره نیست.

### 4.7 نشست

`Session` ورود معتبر Server Side برای یک کاربر است.

وضعیت‌های قطعی:

- `active`
- `revoked`
- `expired`

نشست فقط شناسه غیرقابل‌حدس را در مرورگر حمل می‌کند و تمام معنای امنیتی آن در سمت سرور نگهداری می‌شود.

## 5. شناسه ورود و ایمیل

1. شناسه ورود نسخه نخست ایمیل است.
2. ایمیل برای مقایسه و یکتایی با حذف فاصله ابتدا و انتها و تبدیل بخش‌های حروفی به حروف کوچک نرمال می‌شود.
3. ایمیل نرمال‌شده در سطح سامانه یکتا است.
4. پیام عمومی ورود ناموفق نباید تفاوت میان ایمیل ناشناخته و گذرواژه نادرست را افشا کند.
5. شماره همراه در این مرحله وسیله ورود نیست.
6. ورود با پیامک، ورود اجتماعی و `SSO` خارج از دامنه مراحل فعلی است.

## 6. سیاست گذرواژه

1. حداقل طول گذرواژه `15` نویسه است.
2. حداکثر طول پذیرفته‌شده `128` نویسه است.
3. تمام نویسه‌های چاپ‌پذیر، فاصله و Unicode پذیرفته می‌شوند.
4. قاعده اجباری ترکیب حرف بزرگ، حرف کوچک، عدد یا نماد وجود ندارد.
5. تغییر دوره‌ای گذرواژه بدون شاهد رخداد امنیتی اجباری نیست.
6. گذرواژه با فهرست مقادیر رایج و افشاشده مقایسه می‌شود.
7. Paste برای سازگاری با Password Manager مسدود نمی‌شود.
8. گذرواژه پیش از Hash به‌صورت معنایی Normalization نمی‌شود.
9. گذرواژه خام هرگز ذخیره، Log، Audit یا در Error بازتاب داده نمی‌شود.
10. تغییر موفق گذرواژه تمام نشست‌های دیگر کاربر را لغو می‌کند.

## 7. ذخیره امن گذرواژه

1. الگوریتم اصلی `Argon2id` است.
2. حداقل کف تنظیمات برابر حافظه `19 MiB`، تعداد تکرار `2` و Parallelism برابر `1` است.
3. `Salt` تصادفی مستقل برای هر اعتبارنامه تولید می‌شود.
4. پارامترهای Hash همراه خروجی ذخیره می‌شوند.
5. تنظیم نهایی بالاتر از کف با Benchmark مرحله `P2.4` تعیین می‌شود.
6. در صورت استفاده از `Pepper` مقدار آن فقط از Secret محیط اجرا خوانده می‌شود.
7. ورود موفق می‌تواند Hash قدیمی را با پارامتر جدید Rehash کند.
8. ذخیره مستقیم Hash سریع یا رمزگذاری برگشت‌پذیر گذرواژه ممنوع است.

## 8. بازیابی گذرواژه

1. Token بازیابی با مولد تصادفی رمزنگاری تولید می‌شود.
2. فقط Hash Token در PostgreSQL ذخیره می‌شود.
3. اعتبار Token برابر `30` دقیقه است.
4. Token یکبارمصرف است.
5. درخواست بازیابی پاسخ عمومی یکسان برای ایمیل موجود و ناموجود دارد.
6. مصرف موفق Token تمام Tokenهای بازیابی قبلی و نشست‌های فعال را لغو می‌کند.
7. Provider نهایی تحویل ایمیل در این مرحله انتخاب نمی‌شود.
8. Contract بازیابی از Provider تحویل مستقل است.

## 9. مدل نشست

1. نشست اصلی مرورگر Server Side و ذخیره‌شده در PostgreSQL است.
2. `JWT` به‌عنوان نشست اصلی مرورگر استفاده نمی‌شود.
3. Secret نشست حداقل `256` بیت تصادفی دارد.
4. فقط Hash Secret نشست در پایگاه داده ذخیره می‌شود.
5. نشست دارای `sessionRevision` است.
6. انقضای عدم فعالیت برابر `8` ساعت است.
7. حداکثر عمر مطلق نشست برابر `7` روز است.
8. تمدید فعالیت هرگز عمر مطلق را افزایش نمی‌دهد.
9. ورود موفق شناسه نشست را ایجاد یا Rotate می‌کند.
10. تغییر گذرواژه، غیرفعال‌شدن کاربر و رخداد امنیتی معتبر نشست‌های مرتبط را لغو می‌کنند.
11. کاربر می‌تواند نشست جاری یا تمام نشست‌های خود را لغو کند.
12. گزینه «مرا به خاطر بسپار» در نسخه نخست وجود ندارد.

## 10. Cookie نشست

در محیط Production نام Cookie برابر `__Host-orgawork-session` است.

ویژگی‌های قطعی:

- `HttpOnly`
- `Secure`
- `SameSite=Lax`
- `Path=/`
- بدون `Domain`
- بدون دسترسی JavaScript

در محیط توسعه محلی HTTP فقط نام بدون پیشوند `__Host-` و بدون ویژگی `Secure` مجاز است.

ذخیره Secret نشست در `localStorage` یا `sessionStorage` ممنوع است.

## 11. محافظت در برابر درخواست جعلی

1. الگوی اصلی `Synchronizer Token` است.
2. Token ضد `CSRF` به نشست وابسته است.
3. درخواست‌های تغییردهنده `POST`، `PUT`، `PATCH` و `DELETE` باید Header با نام `X-CSRF-Token` داشته باشند.
4. Token نامعتبر یا مفقود با کد خطای پایدار رد می‌شود.
5. `SameSite` لایه دفاعی تکمیلی است و جای Token را نمی‌گیرد.
6. Token در URL، Log یا Referer قرار نمی‌گیرد.
7. Rotate یا لغو نشست Token قبلی را نامعتبر می‌کند.

## 12. سازمان جاری

1. سازمان جاری در Session Server Side نگهداری می‌شود.
2. شناسه سازمان ارسالی از Client به‌تنهایی قابل اعتماد نیست.
3. انتخاب سازمان فقط برای عضویت `active` مجاز است.
4. عضویت فعال در هر درخواست سازمانی دوباره اعتبارسنجی می‌شود.
5. تغییر سازمان `sessionRevision` را افزایش می‌دهد.
6. Cache باید حداقل کاربر، نسخه نشست، سازمان و منبع را در کلید داشته باشد.
7. تغییر سازمان Cache و داده سازمان قبلی را نامعتبر می‌کند.
8. Tenant Context پایگاه داده فقط داخل Transaction و با `SET LOCAL` اعمال می‌شود.
9. تنظیم Tenant Context در سطح Session اتصال ممنوع است.
10. نبود سازمان معتبر با خطای پایدار رد می‌شود.

## 13. نقش و مجوز

نقش‌های سازمانی پایه:

- `member`
- `manager`
- `organization_admin`

نقش فنی سراسری:

- `platform_operator`

نقش تیمی مستقل:

- `team_manager`

قواعد قطعی:

1. پیش‌فرض عدم دسترسی است.
2. عدم دسترسی صریح بالاترین اولویت را دارد.
3. نقش فقط یکی از ورودی‌های تصمیم دسترسی است.
4. رابطه کاربر و منبع، تیم، وضعیت منبع، مسئولیت جاری و سازمان می‌توانند در تصمیم اثر داشته باشند.
5. مجوز مشاهده و تغییر مستقل هستند.
6. مدیر سازمان دسترسی ضمنی به تمام محتوای سازمان ندارد.
7. اپراتور فنی سکو دسترسی ضمنی به داده سازمانی ندارد.
8. دانستن شناسه منبع مجوز ایجاد نمی‌کند.
9. تصمیم حساس دارای `reasonCode` و Audit است.
10. کاتالوگ دقیق Permissionها در `P2.9` تثبیت می‌شود و نباید زودتر حدس زده شود.

ترتیب تصمیم دسترسی:

1. هویت و نشست معتبر
2. سازمان جاری معتبر
3. عضویت فعال
4. بررسی عدم دسترسی صریح
5. بررسی Permission، رابطه، تیم و وضعیت منبع
6. ثبت نتیجه حساس

## 14. دعوت و عضویت

1. دعوت به ایمیل نرمال‌شده و سازمان مشخص وابسته است.
2. Token دعوت تصادفی، یکبارمصرف و فقط به‌صورت Hash ذخیره می‌شود.
3. اعتبار دعوت برابر `72` ساعت است.
4. دعوت قابل لغو است.
5. پذیرش موفق وضعیت دعوت را `accepted` و عضویت را `active` می‌کند.
6. پذیرش دعوت سازمان دیگر یا اتصال میان دو سازمان رد می‌شود.
7. دعوت تکراری فعال برای همان ایمیل و سازمان باید با رفتار Idempotent مدیریت شود.
8. Provider نهایی ایمیل خارج از دامنه `P2.1` است.

## 15. تیم

1. هر تیم دقیقاً یک سازمان مالک دارد.
2. عضو تیم باید عضویت فعال همان سازمان داشته باشد.
3. کاربر می‌تواند عضو چند تیم همان سازمان باشد.
4. حذف عضو از تیم عضویت سازمانی را حذف نمی‌کند.
5. حذف یا لغو عضویت سازمانی تمام عضویت‌های تیمی آن سازمان را بی‌اثر می‌کند.
6. مدیر تیم مجوز ضمنی همه منابع تیم را ندارد.
7. رابطه میان تیم و عضویت دو سازمان متفاوت در Application و PostgreSQL رد می‌شود.

## 16. Audit و Redaction

رخدادهای زیر Audit امنیتی دارند:

- ورود موفق و ناموفق
- خروج
- ایجاد، Rotate، لغو و انقضای نشست
- تغییر و بازیابی گذرواژه
- تغییر سازمان جاری
- ایجاد، پذیرش، لغو و انقضای دعوت
- تغییر وضعیت کاربر و عضویت
- تغییر نقش، Permission و تیم
- تصمیم‌های حساس اجازه و عدم اجازه

موارد زیر در Audit یا Log ذخیره نمی‌شوند:

- گذرواژه
- Secret نشست
- Token بازیابی
- Token دعوت
- Token ضد `CSRF`
- Cookie کامل
- Authorization Header
- Connection String دارای Credential

## 17. قرارداد معنایی API

مسیرهای دقیق در OpenAPI مرحله مالک ثبت می‌شوند ولی Namespace و عملیات پایه از این مرحله ثابت هستند.

### احراز هویت

- `POST /v1/auth/login`
- `POST /v1/auth/logout`
- `POST /v1/auth/logout-all`
- `GET /v1/auth/session`
- `POST /v1/auth/password-reset/request`
- `POST /v1/auth/password-reset/confirm`

### سازمان جاری

- `GET /v1/organizations`
- `POST /v1/auth/current-organization`

### دعوت، عضویت و تیم

- `POST /v1/organizations/{organizationId}/invitations`
- `POST /v1/invitations/{token}/accept`
- `DELETE /v1/organizations/{organizationId}/invitations/{invitationId}`
- `PATCH /v1/organizations/{organizationId}/memberships/{membershipId}`
- `POST /v1/organizations/{organizationId}/teams`
- `PATCH /v1/organizations/{organizationId}/teams/{teamId}`
- `POST /v1/organizations/{organizationId}/teams/{teamId}/members`
- `DELETE /v1/organizations/{organizationId}/teams/{teamId}/members/{membershipId}`

تمام پاسخ‌های خطا از Error Envelope مصوب پروژه استفاده می‌کنند.

## 19. تصمیم‌های عمداً باز

موارد زیر در این قرارداد مقدار حدسی نمی‌گیرند:

- Provider نهایی ایمیل
- Provider نهایی پیامک
- آستانه دقیق Rate Limit عملیاتی
- کاتالوگ کامل Permissionها
- سیاست Break Glass
- ورود دومرحله‌ای
- ورود اجتماعی و `SSO`
- نام تجاری فارسی رابط

مالک بسته‌شدن:

- Benchmark Hash در `P2.4`
- Rate Limit ورود در `P2.5` و مقاوم‌سازی `P10`
- Permission Catalog در `P2.9`
- Provider تحویل در `P5` یا تصمیم مستقل آینده
- Break Glass در `P10` مگر آنکه زودتر تصویب شود
