# خط‌مبناهای مصوب OrgaWork

## 1. شناسنامه سند

- شناسه سند: `APPROVED-BASELINES`
- نسخه بازبینی‌شده: `0.3.1`
- وضعیت: خلاصه الزام‌آور خط‌مبناهای پذیرفته‌شده پیش از توسعه
- تاریخ بازبینی فنی: `2026-08-04`
- شاخه مرجع: `main`
- دامنه: محصول، معماری، دامنه، داده، قرارداد، تجربه کاربری و آمادگی توسعه
- مرجع وضعیت اجرا: `PROJECT-STATUS.md`
- مرجع ترتیب اجرا: `ROADMAP.md`
- مرجع تصمیم‌های اجرایی جاری: `DECISIONS.md`
- مرجع واژگان و ناوردای‌ها: `DOMAIN-GLOSSARY.md`

این سند خلاصه دائمی تصمیم‌ها و خط‌مبناهایی است که در فاز `P0` پذیرفته شدند و اجازه آغاز توسعه را ایجاد کردند.

این سند جایگزین نسخه کامل تاریخی اسناد اصلی نیست.

## 2. محدودیت منبع و اصل امانت

نسخه کامل تاریخی برخی اسناد اولیه اکنون به‌صورت فایل مستقل در مخزن جاری موجود نیست.

بنابراین این سند:

- فقط تصمیم‌های قطعی و شناخته‌شده را ثبت می‌کند؛
- جزئیات نامطمئن را به‌عنوان واقعیت تاریخی بازسازی نمی‌کند؛
- نام جدول، ستون، Endpoint، Payload، کد خطا یا Provider را حدس نمی‌زند؛
- وضعیت «پذیرفته‌شده» را با «پیاده‌سازی‌شده» یا «بسته‌شده» یکسان نمی‌داند؛
- بسته آرشیوی را منبع الزام‌آور تلقی نمی‌کند؛
- هر جزئیات جدید را به مرحله مالک و Contract رسمی واگذار می‌کند.

اگر نسخه اصلی یکی از خط‌مبناها در آینده پیدا شود، باید با این خلاصه مقایسه شود. اختلاف‌ها نباید بدون بررسی و ثبت تصمیم جایگزین اصلاح شوند.

## 3. سطوح اتکا

در این سند سه سطح اتکا استفاده می‌شود.

### 3.1 قطعی شناخته‌شده

تصمیمی که در چند منبع پروژه تکرار شده، با ساختار فعلی مخزن سازگار است و به‌عنوان الزام جاری پذیرفته می‌شود.

### 3.2 اصل پذیرفته‌شده با جزئیات مرحله‌ای

اصل تصمیم پذیرفته شده است، اما نام دقیق Contract، Schema، State، Provider یا مقدار عددی باید در مرحله مالک تثبیت شود.

### 3.3 غیرقابل بازسازی

جزئیاتی که منبع کافی ندارند در این سند ثبت نمی‌شوند و نباید از روی حافظه ساخته شوند.

## 4. وضعیت‌های معتبر

هر خط‌مبنا می‌تواند یکی از وضعیت‌های زیر را داشته باشد:

- `پیشنهادشده`
- `پذیرفته‌شده`
- `پیاده‌سازی‌شده`
- `آزموده‌شده`
- `بسته‌شده`
- `جایگزین‌شده`
- `لغوشده`

تعریف‌ها:

### پیشنهادشده

هنوز اجازه اجرای الزام‌آور ایجاد نمی‌کند.

### پذیرفته‌شده

اصل تصمیم یا قرارداد تصویب شده است، اما لزوماً پیاده‌سازی یا آزموده نشده است.

### پیاده‌سازی‌شده

کد یا ساختار لازم ایجاد شده است، اما ممکن است پذیرش کامل نباشد.

### آزموده‌شده

رفتار مورد نظر با آزمون واقعی مرتبط تأیید شده است.

### بسته‌شده

تمام معیارهای مرحله، مستندات، Commit، Tag و فضای کاری پاک تأیید شده‌اند.

### جایگزین‌شده

تصمیم توسط سند جدیدتر با دلیل و مسیر مهاجرت جایگزین شده است.

### لغوشده

تصمیم پیش از اجرا یا ادامه رسمی کنار گذاشته شده و دلیل آن ثبت شده است.

هیچ تصمیم پذیرفته‌شده‌ای صرفاً با ایجاد کد، Build یا Mock «آزموده‌شده» یا «بسته‌شده» محسوب نمی‌شود.

## 6. وضعیت

- دامنه اجرا: تمام مراحل `P1` تا `P12`

## 7. مسئله محصول

سامانه باید امور سازمانی پیگیری‌محوری را مدیریت کند که:

- در یک اقدام فوری پایان نمی‌یابند؛
- به پیگیری آینده نیاز دارند؛
- ممکن است به شخص یا تیم دیگری واگذار شوند؛
- ممکن است منتظر پاسخ داخلی یا خارجی بمانند؛
- ممکن است با مانع روبه‌رو شوند؛
- ممکن است موقتاً متوقف شوند؛
- ممکن است نیازمند تصمیم باشند؛
- باید قابل یادآوری و گزارش باشند؛
- باید مسئول، کار جاری و تاریخچه روشن داشته باشند.

## 8. اهداف الزام‌آور

محصول باید:

- احتمال فراموش‌شدن کار را کاهش دهد؛
- مسئول اصلی جاری را روشن نگه دارد؛
- کار جاری معتبر را مشخص کند؛
- نتیجه و ادامه معتبر را باهم ثبت کند؛
- یادآور را در زمان مناسب ایجاد کند؛
- تحویل اعلان را به حضور کاربر در همان رایانه محدود نکند؛
- ارجاع و انتقال مسئولیت را پشتیبانی کند؛
- دید عملیاتی و تاریخی مدیر را در دامنه مجاز فراهم کند؛
- داده سازمان‌ها را سخت‌گیرانه جدا نگه دارد؛
- تغییرات حساس را قابل ردیابی کند.

## 9. اصول مادر

- محصول چندکاربره و چندسازمانی است.
- رابط عمومی فارسی و راست‌به‌چپ است.
- تاریخ‌های ورودی و نمایشی عمومی شمسی هستند.
- زمان پایدار و انتقالی فنی UTC است.
- سیاست دسترسی پیش‌فرض، عدم دسترسی است.
- هیچ پرونده فعالی نباید بدون ادامه معتبر رها شود.
- مسئولیت اصلی و کار جاری نباید مبهم باشند.
- تصمیم حساس بدون مجوز معتبر اجرا نمی‌شود.
- قابلیت نمایشی، Mock یا Runtime حافظه‌ای به معنی تکمیل نیست.
- بسته آرشیوی مرجع وضعیت جاری نیست.

## 10. مرز نسخه نخست

نسخه نخست:

- یکپارچه ماژولار است؛
- Microservices نیست؛
- Event Sourcing کامل منبع حقیقت آن نیست؛
- موتور آزاد طراحی گردش کار توسط کاربر نیست؛
- جایگزین کامل ERP، CRM یا BPM نیست.

# ADR-002 — معماری چندسازمانی و جداسازی داده

## 15. وضعیت

- سطح اتکا: قطعی شناخته‌شده
- وضعیت خط‌مبنا: پذیرفته‌شده
- مالک اصلی: `P1.5` و `P2`
- اهمیت: امنیتی و بحرانی

## 16. تصمیم

- پایگاه داده تجاری مشترک است.
- Schema اصلی مشترک است.
- هر منبع سازمانی سازمان مالک دارد.
- جداسازی فقط در UI یا API انجام نمی‌شود.
- PostgreSQL باید جداسازی سطری را اعمال کند.
- زمینه سازمان جاری در تراکنش معتبر تنظیم می‌شود.
- نقش عادی برنامه نباید امکان عبور از RLS داشته باشد.

## 17. قواعد یکپارچگی سازمانی

- رابطه دو منبع سازمانی نباید منابع دو سازمان متفاوت را به هم متصل کند.
- در صورت نیاز باید محدودیت مرکب استفاده شود.
- Search، Report، Read Model، Queue، Worker، Scheduler و File مشمول همان جداسازی‌اند.
- دانستن شناسه منبع مجوز ایجاد نمی‌کند.
- تغییر سازمان جاری باید Cache و داده قبلی را پاک کند.

## 18. آزمون‌های اجباری

حداقل سناریوها:

- عضو مجاز همان سازمان؛
- عضو بدون مجوز همان سازمان؛
- عضو سازمان دیگر؛
- کاربر بدون عضویت؛
- منبع سازمان دیگر؛
- رابطه مرکب بین دو سازمان؛
- پیام صف با سازمان نادرست؛
- Search مختلط؛
- Report مختلط؛
- File متصل به منبع سازمان دیگر؛
- نشت زمینه سازمان در Pool اتصال.

- نتیجه بدون ادامه معتبر ثبت نمی‌شود.

- مسئولیت اصلی فعال یکتا است.
- انتقال وضعیت نامعتبر رد می‌شود.

- اجرای تکراری فرمان نباید اثر تجاری تکراری ایجاد کند.

- `IdempotencyKey` از اثر تکراری عملیات حساس جلوگیری می‌کند.

در نسخه نخست:

- جدول وضعیت فعلی باقی می‌ماند؛
- Event Store منبع اصلی داده نیست؛
- تبدیل به Event Sourcing کامل نیازمند ADR جدید است.
